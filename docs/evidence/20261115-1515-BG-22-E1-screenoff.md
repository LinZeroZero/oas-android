# BG-22 · E1 熄屏实验（真熄屏 65s，只观测不 detach）

> 时间：2026-11-15 15:12–15:16（设备本地）｜分支 `feat/bg22-setSurface`，代码基线 `656ec1a`
> 执行：OAS-A4（写手）｜判读与落盘：主 AI
> 全部数据为真机实测原始值，未做任何修饰。

## 一句话结论

**判据矩阵命中 ①：熄屏期间 `frames` 仍在增长（+289），心跳连续（C 段 65/65 行、`maxGap 1001ms`）→ BG-22「熄屏时虚拟屏继续合成」成立，`setSurface(null)` 有省电收益。** 本轮按用户口径**不合 main、不打 tag**，去留待拍板。

## 环境

- Android 14 / SDK 34 / RMX3560 / `RMX3560_14.0.0.932(CN01)`；主屏 1080×2412 @480dpi
- 虚拟屏：`oas-e1`，1280×720 @240dpi，`flags=16457`（PUBLIC|OWN_CONTENT_ONLY|SUPPORTS_TOUCH|OWN_FOCUS）→ **`displayId=27`（禁写死）**
- 游戏：`com.netease.onmyoji/com.netease.onmyoji.Client`（`am force-stop` 后**直启 `.Client`**，绕开 BG-27 跳屏）
- daemon：常驻 `app_process`，抽象 socket `oas.chan`，pid **20643**，全程未重启
- 客户端通道：**proot `python3` 直连抽象 socket**，命令必须以 `\n` 结尾（不带换行服务端 `readLine` 阻塞 → `TimeoutError`）

## 方法

1. `create oas-e1 1280 720 240 16457` → `displayId=27`
2. `am force-stop com.netease.onmyoji` → `am start --display 27 -n com.netease.onmyoji/com.netease.onmyoji.Client` → `sleep 5`
3. 出帧确认：`stats 27` 两次（间隔 3s）→ frames **101 → 118**（递增）
4. 冒烟：`kb run 0 0 5 27 /data/local/tmp/kb/smoke.txt` → `n/4 = 1/4`（A/B 0 秒段 FAIL 属预期），C 段 `maxGap 1001ms`、frames 908→1059（**+151**）
5. 完成信号：`am start -a android.intent.action.SET_TIMER --ei …LENGTH 180 --es …MESSAGE "OAS E1 已完成" --ez …SKIP_UI true`
6. 正式：`kb run 5 5 65 27 /data/local/tmp/kb/e1.txt`（只取 ack，不等）
7. 时序（root shell 一次性跑完）：`sleep 12 → input keyevent 26`（熄屏）→ `sleep 75 → input keyevent 26`（唤醒）→ 采 `suspend_stats` / `dumpsys power` / `ps`
8. 收尾：停游戏、`destroy 27`、`monkey` 拉回 Operit、`cat /sys/power/wake_lock`、`rm` 临时文件

## 原始数据（`/data/local/tmp/kb/e1.txt`）

| 段 | 时长 | 行数 | maxGap | frames | 判定 |
|---|---|---|---|---|---|
| A | 5009 ms | 6 | 1001 ms | 1645 → 1812（**+167**） | pass |
| B | 5008 ms | 5 | 1000 ms | 1842 → 1963（**+121**） | pass |
| **C（跨熄屏）** | **65104 ms** | **65** | **1001 ms** | **1994 → 2283（+289）** | **pass** |
| TOTAL | 75 s | 76 | — | 1645 → 2283（**+638**） | **`n/4 = 4/4`** |

对照：冒烟 `kb run 0 0 5` = `n/4 1/4`、C 段 +120 帧 → 帧增长不是「空跑也涨」。

## 物理时序（epoch 秒，设备时钟）

```
S（时序脚本起点）        = 1794726751
C start                 = 1794726754.756
熄屏 OFF                = 1794726763      （= C_start + 8.2s，非计划的 12s）
唤醒 WOKE               = 1794726838      （= OFF + 75s）
C 段结束                = 1794726819.86   （= WOKE − 18s，即**熄屏窗口 100% 落在 C 段内**）
其它同时刻旁证：15:15:26 计时器全屏页拉起并点亮屏幕 → 15:15:32 用户解锁
```

**偏差记录（不修饰）**：`a` 计划 12s，实测 8.2s —— 因为先发 `kb run` 再发时序脚本，两条工具调用之间有 3–4s 延迟；`conn` 结论不受影响（熄屏发生在 C 段第 8 秒，唤醒在 C 段结束后 18s，C 段全程覆盖熄屏态）。

## 探针与数据缺口

| 探针 | 值 | 说明 |
|---|---|---|
| `/sys/power/suspend_stats/success` | 1165 → **1165（delta 0）** | 与该口径的历史结论一致：本机灭屏待机**不进 suspend**，此探针在本机不可用作判据，仅作记录项 |
| `dumpsys power mWakefulness` | `Awake`（唤醒后采） | — |
| `dumpsys power mHoldingDisplaySuspendBlocker` | `true`（唤醒后采） | **数据缺口：熄屏期间未采样**（时序脚本只在唤醒后读），因此「detach 是否解除该锁」本轮仍未验，`DisplayEngine` 注释里的断言依旧只能算推断（见 BG-28 ⑤） |
| daemon 存活 | 唤醒后 **pid 20643 仍在**、`/proc/net/unix` 命中 `oas.chan`、`list` 可达 | 过程中曾出现「ps 里没有 daemon」的假阴性：`ps -A` 只显示进程名 `app_process`，须 `ps -A -o PID,ARGS \| grep oas.chan` |

## 干扰记录（重要，避免下一个人重查）

1. **完成信号确实生效**：`SET_TIMER` + `SKIP_UI` 走的是 `com.coloros.alarmclock/…/timer.TimerAlertFullScreen` 全屏页，15:15:26 拉起并点亮屏幕（此前只验证过 20s 试响，本轮首次在正式实验中确认「响铃 + 亮屏」）。
2. **主屏在实验收尾时自行旋转过两次**：`15:15:32.528 ROTATION_0→90`、`15:15:35.581 90→0`。
   - `RotationHistory` 责任源：`com.ai.assistance.operit/.ui.main.MainActivity`、`SCREEN_ORIENTATION_UNSPECIFIED`、`mode=USER_ROTATION_FREE`
   - 发生时刻 **在 C 段结束之后**（C end 15:15:20.9 → 旋转 15:15:32.5），**不影响本轮任何采集值**
   - 已排除项：仓库 2706 文件 0 处写旋转；本机 `monkey` **无 `--pct-rotation` 事件源**（生成不出旋转事件）；「全屏横屏闹钟」单因素复现**阴性**（亮屏态、锁屏态各复现一次，`accelerometer_rotation` 与 `mUserRotationMode` 均无变化）
   - 待查：见 BACKLOG **BG-31**（现场监视已部署，见下节），本轮**未定责**
3. **时序脚本第 2 个 `input keyevent 26` 打空了**：唤醒在 `15:14:37` 生效，但屏幕 `15:14:40` 又熄灭，直到 15:15:26 闹钟才重新点亮 —— 下次唤醒后应加一次 `dumpsys power` 复核 `mWakefulness`，而不是只依赖 keyevent 返回。

## 判据与结论

| 判据（已定稿，开跑前锁定） | 本轮实测 | 命中 |
|---|---|---|
| ① `frames` 仍增 + 心跳连续（C 段 65/65、`maxGap ≤1500ms`） | +289 帧；65 行；maxGap 1001ms | **是** |
| ② `frames` 停增 + 心跳连续 | — | 否 |
| ③ `frames` 停增 + 心跳断/daemon 消失 | — | 否 |

**结论：BG-22 机制在熄屏态成立 —— 主屏熄灭时虚拟屏仍在持续合成与出帧（+289/65s ≈ 4.4 fps 心跳采样下的持续增长），`setSurface(null)` 具备省电收益。** 去留由用户拍板；按既定口径本轮不合并、不打 tag。

## 复现命令块

```sh
# 全部在 root shell 里跑；daemon 必须先 cd /data/local/tmp 再起（否则 JVM 启动期 SIGSEGV，BG-26）
cd /data/local/tmp

# 客户端（proot 里跑，注意结尾的 \n）
python3 -c "import socket; s=socket.socket(socket.AF_UNIX); s.settimeout(8); s.connect('\0oas.chan'); s.send(b'create oas-e1 1280 720 240 16457\n'); print(s.recv(65536).decode())"

am force-stop com.netease.onmyoji
am start --display <id> -n com.netease.onmyoji/com.netease.onmyoji.Client
sleep 5

# 出帧确认 + 冒烟
python3 -c "… send(b'stats <id>\n')"     # 两次，间隔 3s，frames 必须递增
python3 -c "… send(b'kb run 0 0 5 <id> /data/local/tmp/kb/smoke.txt\n')"

# 完成信号（180s）
am start -a android.intent.action.SET_TIMER --ei android.intent.extra.alarm.LENGTH 180 \
  --es android.intent.extra.alarm.MESSAGE "OAS E1 已完成" --ez android.intent.extra.alarm.SKIP_UI true

# 正式 E1
python3 -c "… send(b'kb run 5 5 65 <id> /data/local/tmp/kb/e1.txt\n')"

# 时序（a 记实际值！并要求唤醒后复核 mWakefulness）
sleep 12; input keyevent 26
sleep 75; input keyevent 26
cat /sys/power/suspend_stats/success
dumpsys power | grep -E 'mWakefulness=|mHoldingDisplaySuspendBlocker'

# 收尾
am force-stop com.netease.onmyoji
python3 -c "… send(b'destroy <id>\n')"
monkey -p com.ai.assistance.operit -c android.intent.category.LAUNCHER 1
cat /sys/power/wake_lock          # 期望为空
rm -f /data/local/tmp/kb/smoke.txt
```

## 未验 / 后续
