- 执行：写手 A4（唯一写手位）｜派单与数字复核：主 AI
- 环境：daemon pid **20643**（复用，`/data/local/tmp/server.jar` 不存在）｜虚拟屏 `oas-a1` **displayId=31**（1280×720@320，flags=9）｜游戏 `com.netease.onmyoji` pid **29273**
- 判据（用户拍板，双档）：daemon+游戏 jiffies 降幅 **≥50% → 有收益**；**<20% → 零收益**；20–50% → 弱收益（回用户二次拍板）

## 2. 计算

| 组 | 窗口 | Δdaemon | Δ游戏 | ΣΔjiffies | 归一（jiffies/s） |
|---|---|---|---|---|---|
| **off**（不 detach） | 89 s | +7 | +1023 | **+1030** | **11.57** |
| **on**（熄屏第 1 秒 detach） | 78 s | +3 | +1033 | **+1036** | **13.28** |

**降幅 = (11.57 − 13.28) / 11.57 = −14.8%（负值，即 on 组每秒 CPU 反而略高）→ 落在「<20% = 零收益」档。**

旁证：detach 期间 `frames` 8188→8188（冻结），说明**确实停渲**（输出端被摘），但停渲**没有**换到可测的 CPU 节省。

## 3. 结论（按预注册判据，不含事后改判）

- **判据命中「零收益」**：熄屏 detach 相对不 detach，未带来 ≥20% 的 CPU 降幅，更谈不上 ≥50%。
- 与 E3 合并看：detach 换不来更深休眠（E3），也换不来可测的 CPU 节省（本测）→ 收益假设**未获支持**。

## 4. 本测的已知缺陷（必须与结论一起读，不许只引用结论）

1. **判据模板漏了合成器进程**：按模板只采 daemon + 游戏；`setSurface(null)` 的预期节省应主要落在 `surfaceflinger`（pid 1284）与 system_server 合成侧。本次**未采 SF 前后值**，因此严格说「零收益」是指在**预注册口径**下零收益；要否定「SF 侧有收益」还需一次把 SF 纳入的重测。
2. 两组**窗口不等长**（89 s vs 78 s），已按 jiffies/s 归一；两组为**串行**非交叉对照。
3. 背景负载偏高且抖动（loadavg 16.29–20.52，4 核），对 ±15% 量级差异的置信度有限。
4. 是**一次**取样，n=1，未做重复窗口。

## 5. 新发现的负面行为（重要，独立于判据）

**`attach` 之后画面未恢复出帧**：16:43:22 `surface attach 31` 返回 `{"ok":true,"displayId":31}`，但 `frames` 在 16:43:21 / 16:43:27 / 16:47:46 三次采样恒为 **8188**（游戏进程 29273 仍在、daemon 正常），而 E2（亮屏 detach→attach）时 frames 曾从 479 恢复到 905。

差异候选原因（未验，仅登记）：本次 detach 横跨「熄屏 → 亮屏」窗口，游戏在虚拟屏失去输出端后被 pause/失去可见性，attach 只是重新挂面、不会重新拉起渲染。若上线（哪怕默认关、用户手动开），这就是「亮屏后游戏不刷新」的风险面。
