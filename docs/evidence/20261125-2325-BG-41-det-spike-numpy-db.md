# BG-41 spike：det 链路可行性（PP-OCRv3_det + 纯 numpy DB 后处理）

## 1. 日期 / 环境
- 2026-11-25 23:2x（CST）；分支 `main`；HEAD 以 `git log --oneline -1` 现查
- **proot Ubuntu / aarch64**，`onnxruntime==1.20.0`（CPU EP）、PIL 10.2.0；**无 cv2、无 pyclipper、无 scipy**
- 模型（本地已有，未下载）：`ch_PP-OCRv3_det_infer.onnx` = **2,432,880 B**（动态输入 `[None,3,'?','?']`）、`ch_PP-OCRv2_rec_infer.onnx` = 8,361,244 B、`ppocr_keys_v1.txt`

## 2. 目的
BG-41 的唯一技术风险是：**没有 cv2/pyclipper 时，DB 后处理能不能用纯 numpy 做出来**。本 spike 只回答这一个问题，不动 `app/`。

## 3. 做法（纯 numpy，矩形近似 unclip）
1. 长边缩到 960、32 对齐（本例 1080×2412 → **416×960**），`mean/std=(0.485,0.456,0.406)/(0.229,0.224,0.225)`
2. det 前向 → 概率图 `(960,416)`，`thr=0.3` 二值化
3. 4× max-pool 降采样后在**小图上做 BFS 连通域标注**（纯 python，避免逐像素扫全图），取外接矩形、丢弃 <8px 的碎片
4. 映射回原图，**外扩 15%** 作为 unclip 的矩形近似
5. 逐框裁剪 → 现有 rec（`[3,32,W]`，`[-1,1]` 归一化）→ CTC 贪心解码

## 4. 四段原始数字

## 5. 结论
- **可行性成立**：**不需要 cv2 / pyclipper / scipy**，纯 numpy + PIL 就能走完「det → 框 → 裁剪 → rec」，真实中文界面识别分数 0.88–1.00（干净行）。
- **代价**：det 382 ms + 25 框 rec 981 ms ≈ **1.4 s/整屏**（proot CPU，n=1）。OAS 的 `Full`/`Quantity` 通常只 OCR 一个区域，框数远少于 36；但**整屏调用会很慢**，需在实现时限制 `max_boxes`。
- **已知失真**：矩形近似会把同一行的多段文字并成一框（本例 #22–#25 是整行 1000px 宽），多列布局可能串行；真正修复需多边形 unclip（Vatti 裁剪），成本高。
- **未测**：方向分类（cls 模型在本地但未接）、`thr`/外扩比只试了 0.3/15%、竖排、深色背景、APK 内。按 **D-018 全部不作性能结论**（n=1 图、n=1 参数）。

## 6. 给 BG-41 实现的建议
1. 先落**矩形近似**版（能立刻让 `Full`/`Quantity` 从"抛异常"变"可用"），`max_boxes` 默认 20、`thr=0.3`；
2. 后处理放 Python（numpy）侧、模型走 Kotlin `OcrRuntime`（沿用 BG-40 的分层），避免 Python 侧调 JNI 做逐元素转换；
3. 模型入 `assets/`：det 2,432,880 B → APK 约 +2.4 MB，`THIRD_PARTY_NOTICES` 补 ppocr-onnx det 型号；
4. 多边形 unclip 立后续项（BG-42 之后），不进第一版。
