# BG-22 · 预实验 E2：`setSurface(null)` 到底能不能解掉电源锁（+ 公开 API 核查）

> 时间：2026-11-15 15:41–15:47（设备本地）｜分支 `feat/bg22-setSurface`，代码基线 `656ec1a`
> 执行：OAS-A4（只取证，全程**亮屏**、不改设置、不改代码、不 commit）｜调研：OAS-D｜判读与落盘：主 AI
> 起因：用户质疑 BG-22 那句「既保留虚拟屏又不让系统拿 SCREEN_BRIGHT 锁，**无公开 API 可走**」，要求查官网与 GitHub 后复查。

## 一句话结论

1. **`setSurface(null)` 确实解掉了那把锁**：detach 后 `dumpsys power` 里 `SCREEN_BRIGHT_WAKE_LOCK 'WindowManager/displayId:28'` 整行消失、出现 `REL WindowManager/displayId:28`（15:43:16.113），display state 变 `OFF`、viewport `isActive=false`、frames 冻结 479→479；attach 后锁重新 ACQ、state 回 `ON`、frames 恢复 905。**BG-22 的生产方案在电源侧是真有效的，不只是停渲。**
2. **「无公开 API 可走」这句要改**：官方文档对 `VirtualDisplay#setSurface` 的原话是「**摘除 backing surface 与关屏效果类似**」，也就是说 `setSurface(null)` 不是「绕路」，而是官方指定的等价关屏手段；另一条隐藏路径（`SurfaceControl.setDisplayPowerMode`）**取不到虚拟屏的 display token**，实际不可用。
3. **仍有一个缺口**：`mHoldingDisplaySuspendBlocker` 在主屏亮着时恒为 `true`（主屏自己也持锁），所以「detach 后整机能不能真睡」必须在**熄屏态**下测 —— 见 E3。

## 环境与方法

- 虚拟屏 `oas-e2` 1280×720@240、`flags=16457` → **`displayId=28`**；其上 `am force-stop` 后直启 `com.netease.onmyoji/.Client`
- daemon 沿用常驻 `oas.chan`（pid 20643，未重启）
- 方法：基线采集 → `surface detach 28` → 采一次 → `stats` 两次确认冻结 → `surface attach 28` → 采一次
- 四条探针（每条都留原文）：
  - 4a `dumpsys power | grep -nE 'mWakefulness|mHoldingDisplaySuspendBlocker|SCREEN_BRIGHT'`
  - 4b `dumpsys power` 里 `displayId:<id>` 段的锁明细（ACQ/REL 时间）
  - 4c `dumpsys display | grep -iE 'oas-e2|mDisplayState|DisplayDeviceInfo'`
  - 4d `dumpsys SurfaceFlinger --display-id`（看能否拿到虚拟屏 token）

## 公开 API 核查（两条独立证据）

**本地（主 AI，硬证据）**：本机 SDK 公开 `android.jar`（`/root/Android/platforms/android-35/android.jar`）解包 ——
- `android/view/SurfaceControl$Transaction` 的 `set*` 只有 `setAlpha/setCrop/setLayer/setPosition/setScale/setVisibility/setBufferSize/setGeometry/setFrameRate…`，**`setDisplayPowerMode` 计数 0**
- `android/hardware/display/VirtualDisplay` 公开方法只有 `setSurface / getSurface / resize / release / getDisplay`

**AOSP 源码（OAS-D）**：
- `core/java/android/view/SurfaceControl.java:2060-2068` — `setDisplayPowerMode(IBinder, int)` 是 **`public static` 但 `@hide`**；`POWER_MODE_OFF=0` 在 `:925-959`（同 `@hide`）；`Transaction` 上无此方法
- `SurfaceFlinger.cpp:5600/5603` — SF 侧最终走 `getHwComposer().setPowerMode(displayId, mode)` → 虚拟屏无 HWC 显示，**预期 no-op**（推断）
- `frameworks/base/.../VirtualDisplayAdapter.java:372` 构造时 `mDisplayState = STATE_ON`；`:641-645` 仅当 `mSurface == null` 才置 `STATE_OFF`（→ **状态跟 surface 走，不跟 power 请求走**）
- `PowerManagerService.java:433 / :3858-3888` — `mHoldingDisplaySuspendBlocker` 按**全局 wakefulness** 计算，没有 per-display 参数入口

**官方文档（OAS-D 取原文）**：`VirtualDisplay#setSurface(Surface)`（API 20 起）——
> "Sets the surface that backs the virtual display. **Detaching the surface that backs a virtual display has a similar effect to turning off the screen.** It is still the caller's responsibility to destroy the surface after it has been detached."

## 判读

- BG-22 原方案（主屏熄屏时 `setSurface(null)`）**在电源侧有效**：per-display 的 `SCREEN_BRIGHT` 锁被真正释放（有 `REL` 记录），display state 转 `OFF`，且可逆。
- 「无公开 API 可走」**表述不准确**，应改为：官方文档明确把「摘除 surface」定义为等价关屏；隐藏路径 `SurfaceControl.setDisplayPowerMode` 存在但（a）拿不到虚拟屏 token、（b）对虚拟屏预期 no-op —— 因此**没有比 `setSurface(null)` 更便宜的第二条路**。
- 未决：主屏熄屏 + 虚拟屏 detach 时，`mHoldingDisplaySuspendBlocker` 是否随主屏变 `false`（即整机可睡）。主屏亮着时它恒 `true`，本轮无法区分。

## 未验 / 下一步

1. **E3（熄屏 3 组对照，需用户在场）**：① 无虚拟屏（基线）；② 虚拟屏 attach；③ 虚拟屏 detach —— 每组熄屏 ~25s，只读 `dumpsys power | grep -E 'mWakefulness|mHoldingDisplaySuspendBlocker'` 与 `cat /sys/power/wake_lock`。判据：若 ③ 与 ① 同值（`false`）而 ② 为 `true`，则 BG-22 省电收益被**端到端**证实。
2. 不要再用 `suspend_stats/success` 作判据：本机不进 suspend（1165→1165，见 E1）。
3. `setDisplayPowerMode` 路线建议就此封掉，除非将来能拿到虚拟屏 token（当前无公开/无隐藏入口）。
