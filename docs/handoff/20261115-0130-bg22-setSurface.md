## 3. 当前断点

### 3.1 代码停在「零实现」

`poc/displayserver/src/org/onmyoji/oas/server/` 下实际只有 6 个文件：
`DisplayEngine.java` / `SocketServer.java` / `Main.java` / `Heartbeat.java` / `DaemonWakeLock.java` / `KbRun.java`。
**没有 `DisplayServer.java`、也没有 `ApkBridge.java`** —— `DisplayServer` 是 app 侧的 `app/src/main/java/org/onmyoji/oas/android/root/DisplayServer.kt`（Kotlin，socket 客户端）。找服务端代码别找错文件。

`grep -rn 'setSurface\(null\)\|detach'` 全仓 **0 处命中** → 能力未实现。

具体位置：
- `DisplayEngine.create()` / `mirror()`：拿到 `ImageReader` → `surface = reader.getSurface()` → `createVirtualDisplay(config, surface…)` → `register(vd, reader, surface, …)`；`Entry.surface` 就是这个 Surface。
- 拆屏路径只有 `destroy(id)` → `release(entry)`（`vd.release()` + `reader.close()` + `surface.release()`）和 `releaseAll()`。**这两个都不能复用**：它们是「拆屏」，而本棒要的是「留屏、只摘输出端」。
- `SocketServer` 行协议命令表：`ping|create|mirror|grab|stats|list|destroy|hb start|stop|status|watch|exit|kb run|kb stop|kb status`。要新增的命令挂这里。
- `Heartbeat` 每拍取 `framesOf(displayId)` → `DisplayEngine.framesOf()`；摘面后期望 **frames 停增**（这是本棒的观测口）。

### 3.2 要新增的最小面（一次只加一处）

1. `DisplayEngine`：`detach(int id)` → `entry.virtualDisplay.setSurface(null)`（**不 close reader、不动 entry.surface**）；`attach(int id)` → `setSurface(entry.surface)`（同一 Surface 对象可复用，因为 ImageReader 还活着）。两个都要 `synchronized`，且对未知 id 返回 false 而不是抛。
2. `SocketServer`：加 `surface detach <id>` / `surface attach <id>` 两条命令（写进 `help` 的 `cmds` 串）。
3. 触发载体（**默认关**）：daemon 侧不自己监听屏状态（`app_process` 无 Context，收不到 `ACTION_SCREEN_OFF`）。用一个显式开关，例如 `Main --surface-detach-on-screenoff on`（缺省 off）或 app 侧 `--ei vdisplay_detach 1` 后由前台服务在熄屏 broadcast 里发 `surface detach`。**开关缺省必须是 off**，不传 = 与今天行为完全一致。
4. 收尾：`releaseAll()` / `destroy()` 要能处理「已 detach」的 entry（`setSurface(null)` 后再 release 是安全的，但别重复 attach 已 close 的 Surface）。

## 5. 排除记录（已试过，不要再试）

- **`setSurface(null)` 会让虚拟屏瘫面 / 停渲**：这是方案的固有代价，**用户已知情并接受**。不要再拿「游戏会卡住」当反对理由来推翻决策（BACKLOG BG-22 旧表态「暂不采纳」**已作废**，现决策是**采纳、默认关**）
- **`--wakelock on/off` 对照在本机没有灵敏度**：灭屏各 15s，C 段 `maxGap` **1001ms vs 1003ms**（差 2ms，落在 tick 抖动内）。别再拿这组对照当 BG-21/BG-22 证据
- **灭屏待机 20s 根本不进 suspend**：`success` 1164、`fail` 135，t=0/5/12/20 逐点采样**全不动**（fail 不动 = 连失败都没有）。所以「灭屏 N 秒前后 `suspend_stats/success` 差值」这条判据在本机**不可用**，已降级为记录项，不是判据
- **唯一能让 `success` +1 的路**：`echo freeze > /sys/power/state` 显式跌进 s2idle（实测 1164→1165、秒回 `Awake`）。用它可以造「进过 suspend」的证据，但**必须预置 `rtc0/wakealarm` 兜底**（如 `+8s`），否则可能醒不来
- **`env -i` 清空环境绕不过 cwd 坑**：反而变成「`rc=0` 但完全空跑、不产生任何副作用」的结果，比报错更难查。别试
- **`dumpsys deviceidle force-idle`**：`Unable to go deep idle; not enabled`，delta=0；`enable all` + `force-idle` 在亮屏下 5s delta=0，**无解释力**
- **判据/定责里已被推翻的说法，不得重试**（`docs/HANDOFF.md §十二`）：
  - 「游戏自持 `SCREEN_BRIGHT_WAKE_LOCK 'WindowManager/displayId:19'`」→ **错**，持锁者是 `system_server`（uid=1000 pid=2106），`WorkSource{com.netease.onmyoji}` 只是标签
  - 「主屏能熄灭 = 假息屏」→ **不成立**（超时看 `userActivity`、电源键走 `goToSleep`）；真风险是 SCREEN_BRIGHT 计入 `mWakeLockSummary` → 整机不休眠
  - 「用 `PowerManager` 申请/释放锁」→ **不可行**（`app_process` 下 `Workarounds.getSystemContext()` 返回 null，`getSystemService` 必 NPE），只能写内核 sysfs
  - 「文件 socket + `chmod 666`」→ **平台不支持**（API 35 `LocalServerSocket` 只有 `(String)`/`(FileDescriptor)`，名字建在 abstract namespace）
  - 「改 `VIRTUAL_DISPLAY_FLAG` 或改 display power mode 就能让系统放锁」→ 前者无效、后者需 system 权限，**无公开 API**
- 【新】**`--cmd` 是一次性进程，虚拟屏 / daemon 状态不跨进程保留**：它 `new SocketServer(...)` 在本进程内 `exec` 完就 `System.exit(0)`，既不连已有 daemon 也不 bind socket。**需要长期持屏时必须用「常驻 daemon + 独立客户端」，二者不能混用同一条 `--cmd`**；用一次性进程跑出来的 `list` id / `kb run` 数字**不算数据**

**7.3 组 1：feature off（= BG-21 新口径复现组）**

> **形态修正（A4 实测踩到，原文写错）**：`--cmd` 是**一次性进程** —— 它自己 `new SocketServer(...)`，在**本进程内** `server.exec(cmdLine)` 然后 `System.exit(0)`（`Main.java` 的 `cmdLine` 分支），**既不连常驻 daemon、也不 bind socket**。进程一退，它建的虚拟屏随之消失。所以「先 `--cmd list` 取 id，再 `--cmd kb run <id>`」拿不到长期存在的真实 displayId：两条命令是两个互不相干的进程，id 不可能复用。

CLASSPATH=/data/local/tmp/kbdaemon.jar /system/bin/app_process /system/bin \
