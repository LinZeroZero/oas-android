## 1. 当前任务目标

**本棒做 BG-21 的预实验（pilot），不是正式测。** 预实验只回答一个方法学问题：
**这台机器上到底能不能观测到「整机进入 suspend」？** —— `system_server` 正为 `displayId:19` 持有
`SCREEN_BRIGHT_WAKE_LOCK`（`mHoldingDisplaySuspendBlocker=true`），很可能整机根本不进 suspend，
那么 `suspend_stats/success` 恒不变，「60s 后差值」就没有任何解释力。

先跑 P0–P4 五个短实验（每档 ≤20 秒，省机时），产出：
- 探针清单：命令 / 读数口径 / 预期 / 实测
- 阴性对照结果：能不能让 `suspend_stats/success` 真的 +1
- `--wakelock on/off` 这组对照到底有没有灵敏度
- 正式测该用多长时长、`maxGap` 阈值定多少

**做到什么算完（验收口径）**：
1. `docs/evidence/20261115-*-bg21-pilot.md` 里 P0–P4 每项都有原始输出与判定；
2. 三条 gate 明确写出「绿 / 不绿」：G1 四探针都有明确值、G2 至少一条路能让计数 ≥ +1、G3 `kb run` 可直接跑且报告落盘；
3. gate 全绿 → 顺手做正式测（E 段，见 §7 第二块）；不绿 → **不改代码**，把结论与「要不要采纳 `setSurface(null)`」一起报回主 AI；
4. **预实验数据一律不得写进「BG-21 通过/不通过」的结论**，只用于校准方法与阈值。

## 2. 已完成工作

- BG-19：daemon 侧 `kb run <a> <b> <c> <displayId> <reportPath>` 三段计时 + 心跳判读 + txt/json 报告（main `753dd9e`，PR #9）。真机 `kb run 5 5 5 -1 …` → `n/4 = 4/4（全过）`，`maxGap 1001ms`
- BG-23：`--socket` 真参数、按名字 bind 抽象 socket、删掉文件 socket 死代码（main `507574e`，PR #12）
- 当前 `app/src/main/assets/server/server.jar` = **28650 B**（javac 9 文件 / d8 20 class）
- 本机基线（刚刚实测）：`/sys/power/suspend_stats/success` = **1164**，未充电（`AC/USB/Wireless powered: false`），`mWakefulness=Awake`

## 3. 当前断点

- 停在「daemon 侧已经能跑完三段」，但 **C 段从未在真熄屏下跑过**；历史数据（645 拍 / maxGap 1004ms）是后台常驻心跳，不是 C 段
- 工作区干净，`main` 无半成品；不需要回滚任何东西
- 唯一可用的设备侧入口：`super_admin:shell` 起 `app_process`（从 proot / `super_admin:terminal` **连不上抽象 socket**，`/proc/net/unix` Permission denied + `ConnectionRefused`）

## 4. 关键约束

- **绝不** `wm size` / `wm change-density`：识别画布恒定 1280×720，不动物理分辨率与 dpi
- 只准申请 **PARTIAL 语义**锁（内核 `/sys/power/wake_lock`）；**绝对不许** `SCREEN_BRIGHT_WAKE_LOCK` / `FULL_WAKE_LOCK`，主屏必须能被用户正常熄灭
- 测完必须把手机还给用户：**亮屏 + 把 Operit 拉回前台**
- 两次熄屏各约 65 秒，别拖长；两组之间先把锁清空再开始下一组
- 一棒一个目标；只 `git add <具体文件>`，**禁止** `git add -A` / `commit -a`；**禁止** `checkout` / `merge` / `reset` / `tag`
- `super_admin:shell` 会把「`rm -rf` + `ps | grep`」这类复合命令判为危险并拒绝 → 拆成多条执行

## 5. 排除记录（已试过、不要再试）

- 「游戏自持 `SCREEN_BRIGHT_WAKE_LOCK 'WindowManager/displayId:19'`」→ **错**。持锁者是 `system_server`（uid=1000 pid=2106），为 ON 状态的 display 持有系统锁，`WorkSource{com.netease.onmyoji}` 只是标签（BG-22）
- 「主屏能熄灭 = 假息屏」→ **不成立**。主屏可被正常熄灭（超时看 `userActivity`、电源键走 `goToSleep`）；真风险是 SCREEN_BRIGHT 计入 `mWakeLockSummary` 导致**整机不休眠**
- 「wakelock 用 `PowerManager`」→ **不可行**。`app_process` 下 `Workarounds.getSystemContext()` 返回 null，`getSystemService` 必 NPE；只能写内核 sysfs
- 「文件 socket + `chmod 666`」→ **平台不支持**。API 35 的 `LocalServerSocket` 只有 `(String)`/`(FileDescriptor)` 两个构造，官方文档写明名字建在 Linux abstract namespace（BG-23 已删死代码）
- 「`--socket` 换个名字起第二实例」→ 曾经必报 `Address already in use`，`04cf79b` 后已修好，别再当 bug 重报

## 6. 当前故障

1. 无阻断性故障。唯一已知坑：`--cmd` 是**一次性**的（执行完进程就退），所以熄屏动作必须在同一个 shell 里用后台 `sleep` 卡点触发，不能指望「先把 daemon 留着、过一会儿再连」
2. `input keyevent 26` 熄屏后，若亮屏时停在锁屏界面：先 `input keyevent 26` 唤醒，再 `input swipe 540 1800 540 600`；仍不行就在证据里写明并交回主 AI，别自己折腾锁屏

## 7. 启动动作

> **工具分工（实测过的坑）**：工作区/git 走 `super_admin:terminal`（proot）；**摸设备的命令一律走 `super_admin:shell`（root）**。
> 在 proot 里读 `/sys/power/*` 会直接 `Permission denied`（实测），所以下面分两块。

**7.1 工作区自检（terminal）**
```sh
cd /data/user/0/com.ai.assistance.operit/files/workspace/8868caab-ae27-4814-9992-11fb83225a35
git pull --ff-only origin main                      # 本棒基线：main = 41a1826
git log --oneline -1                                # 期望 41a1826
stat -c '%s' app/src/main/assets/server/server.jar   # 期望 28650
git status --porcelain                              # 期望为空
```

**7.2 器材就位（shell，root）**
```sh
cat /sys/power/suspend_stats/success   # 期望 1164，记下当前值
cat /sys/power/wake_lock               # 期望为空
cp /data/user/0/com.ai.assistance.operit/files/workspace/8868caab-ae27-4814-9992-11fb83225a35/app/src/main/assets/server/server.jar /data/local/tmp/kbdaemon.jar
mkdir -p /data/local/tmp/kb
echo ready
```

**7.3 预实验 P0–P4（每档都短，逐条跑）**

- **P0 链路**（不熄屏）：
```sh
CLASSPATH=/data/local/tmp/kbdaemon.jar /system/bin/app_process /system/bin \
  org.onmyoji.oas.server.Main --cmd 'kb run 0 0 3 -1 /data/local/tmp/kb/p0.txt' --wait 15000
cat /data/local/tmp/kb/p0.txt
```
- **P1 探针读数**（四个都要有明确值）：
```sh
cat /sys/power/suspend_stats/success
cat /sys/power/wake_lock
dumpsys power | grep -E 'mWakefulness=|displayId:19' | head -5
```
- **P2 阴性对照（关键，先走安全路径）**：
```sh
B0=$(cat /sys/power/suspend_stats/success); echo "b0=$B0"
dumpsys deviceidle force-idle
sleep 5
B1=$(cat /sys/power/suspend_stats/success); echo "b1=$B1 delta=$((B1-B0))"
dumpsys deviceidle unforce
```
  `delta` 仍为 0 → 才考虑 `echo mem > /sys/power/state`（3s 档、手放电源键兜底）；仍为 0 就把 G2 记为不绿并停。
- **P3 对照灵敏度**（灭屏下各 15s，两组）：把 P0 的命令换成 `--wakelock on` / `--wakelock off`，
  `kb run 0 0 15 -1 /data/local/tmp/kb/p3on.txt` 与 `.../p3off.txt`，比较两组 `maxGap`。
- **P4 时长标定**：`kb run 0 0 10 -1 ...` 与 `kb run 0 0 30 -1 ...` 各一次，看 `maxGap` 抖动幅度，
  给出正式测的建议时长与阈值。

三条 gate：G1（P1 四项有值）/ G2（P2 `delta ≥ 1`）/ G3（P0 落盘且 `n/4` 分母为 4）。

**7.4 正式测 E 段（只有 gate 全绿才做）**
```sh
BEFORE=$(cat /sys/power/suspend_stats/success); echo "before=$BEFORE"
( sleep 12; input keyevent 26 ) &
CLASSPATH=/data/local/tmp/kbdaemon.jar /system/bin/app_process /system/bin \
  org.onmyoji.oas.server.Main --wakelock on \
  --cmd 'kb run 5 5 65 -1 /data/local/tmp/kb/on.txt' --wait 95000
AFTER=$(cat /sys/power/suspend_stats/success); echo "after=$AFTER delta=$((AFTER-BEFORE))"
cat /data/local/tmp/kb/on.txt
```
第二组同上，`--wakelock on` 换 `--wakelock off`、输出改 `/data/local/tmp/kb/off.txt`；两组之间确认 `cat /sys/power/wake_lock` 已空。
（P3 若证明该对照无灵敏度，只做一组并说明理由。）

**7.5 收尾（必须做，一条一条跑）**

input keyevent 26
monkey -p com.ai.assistance.operit -c android.intent.category.LAUNCHER 1
rm -f /data/local/tmp/kbdaemon.jar
